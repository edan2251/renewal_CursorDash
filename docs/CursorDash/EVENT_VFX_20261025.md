## 커서가 뒤에 덮이는 렌더 구조와 수정

정적 소스 추적으로 확인한 덮임 구조는 다음과 같다.

1. 실제 플레이어 `CursorVisual`은 SpriteRenderer이다. 씬 저장값은 layer0, Sprites/Default, sortingOrder2, drawModeSimple, SpriteMask 없음이다. 콜라이더/입력은 부모에 있다.
2. main camera의 월드 렌더 이후 LocalImpactDistortion/원래 Background_Flash/넥서스3이미지를 후처리로 합성한다. **이 뒤늦은 넥서스 합성은 월드 SpriteRenderer의 sortingOrder보다 뒤다.** 따라서 sortingOrder만 올려도 해결할 수 없다.
3. 그 후 UI 전용 카메라(depth main+1, UI layer5)가 안정된 Canvas/HUD를 그리고, RemakeHUD Overlay(정렬25)와 설정 UI가 위에 남는다. 넥서스 원본은 배치/공격경계 참조로 남겨 두고 Image.enabled만 임시로 끈다.
4. D-024는 넥서스 셰이더 안에서 별도의 텍스처 사각형으로 커서를 재구성했다. 실제 SpriteRenderer의 렌더 결과가 아니며 packed sprite 등에서는 아예 생략되는 조건도 있었다. **사용자가 본 실패 프레임에서 그 조건이 원인이었는지, 원본UI가 다시 표시됐는지는 실측하지 못했다.** Play 종료로 해당 인스턴스는 확인할 수 없다.

이번에는 그 사각형 재구성을 제거했다. 실제 CursorVisual 표시 자식만 이름 없는 미사용 레이어(31부터 탐색)에 임시로 분리하고, 부모/위치/입력/물리는 그대로 둔다. 프로젝트 레이어 설정 파일은 바꾸지 않는다. 실제 SpriteRenderer를 같은 뷰/투영의 비활성 보조 카메라로 투명 RenderTexture에 렌더해, **월드·배경 → 넥서스 → 실제 커서 → UI 카메라/HUD/설정** 순으로 합성한다. 원래 월드 패스에서는 이 자식만 제외하므로 두 번 겹쳐 그리지 않는다. Sprite의 atlas/mesh/pivot/색/재질/flip을 추정해서 다시 만들지 않는다. 게임판 왜곡/빛 식은 그대로 재사용하며 커서만 이 새 순서로 표시한다.

이는 Unity의 [별도 비활성 카메라와 Camera.Render](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Camera.Render.html), Built-in의 [OnRenderImage](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/MonoBehaviour.OnRenderImage.html) 경로다. 재귀적으로 main camera를 Render하지 않는다. 레이어/카메라 마스크는 해제 시 복원하며, 원본 SpriteRenderer의 색/정렬값/위치/콜라이더를 수정하지 않는다.

검수창에 넥서스 등록 실패 이유, 실제3원본 enabled/active, 실제 커서 셰이더/packed 여부, 넥서스·커서 합성 호출 수를 표시한다. 넥서스 셰이더 미지원/지원하지 않는 원본 구성일 때 UI 원본을 남기는 기존 보존 fallback은 유지한다. **이 경우 커서 앞 표시가 보장됐다고 처리하지 않는다.** 등록 경고/상태와 최종 Game View를 함께 확인해야 한다. 호출 수가 늘어난다는 것만으로 시각 PASS가 아니다.

추가 비용은 커서1개용 카메라 렌더와 임시RT/전면합성이다. 실제 Unity 및 모바일 성능은 이번에 측정하지 않았다.
